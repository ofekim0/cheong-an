# ADR 017: 크롤 스케줄러 이전 — GitHub Actions schedule에서 외부 cron 서비스로

- **상태**: 제안됨
- **작성일**: 2026-11-23
- **관련 이슈**: #102
- **대체 대상**: ADR 004 (크롤링 스케줄러 선택 — GitHub Actions). 단, `/api/cron/crawl` + `CRON_SECRET` Bearer 인증 구조와 GHA `workflow_dispatch`(수동 실행)는 유지한다

## 맥락

ADR 004는 "한 시간 안에 새 공고를 잡는 것이 알림 가치의 하한선"이라는 전제로 GitHub Actions `schedule`(`cron: '0 * * * *'`)을 골랐다. 무료로 1시간 간격을 돌릴 수 있는 유일한 선택지라는 것이 근거였다.

**그 전제가 실제로는 성립하지 않았다.** `gh run list --workflow=Crawl` 실측:

| 시점                   | 표본                                      | 실행 간격               | 하루 실행 수 |
| ---------------------- | ----------------------------------------- | ----------------------- | ------------ |
| 2026-09-04 (#102 등록) | 최근 10회                                 | 2시간 22분 ~ 4시간 40분 | 7~8회        |
| 2026-11-23             | 최근 15회 (11-18 21:10 ~ 11-23 00:03 UTC) | 3시간 59분 ~ 8시간 58분 | 3~4회        |

모든 회차가 `event=schedule`·`success`이고 실행 시각의 분이 제각각이다. 실패한 것이 아니라 **GitHub가 회차를 발화하지 않은 것**이다. 새 공고가 올라와도 최대 9시간 뒤에야 감지·발송된다.

원인은 GitHub 쪽이라 관찰할 수 없지만, 공개된 동작으로 설명된다.

- `schedule` 트리거는 보장이 아니라 best-effort다. 고부하 시 지연되며, 정시(매시 0분)가 고부하 시간대이고, 부하가 크면 대기 중인 실행이 **버려질 수 있다**. 버려진 회차는 실패로 표시되지 않는다.
- 공개 저장소에서 60일간 저장소 활동이 없으면 예약 워크플로가 자동 비활성화된다고 알려져 있다(공식 문구 미확인). 이 저장소는 main 마지막 머지가 2026-09-04로 이미 60일을 넘겼는데도 아직 실행되고 있어 적용 조건은 확인하지 못했다. 어느 쪽이든 **조용히 멈출 수 있는 경로가 하나 더 있다**는 뜻이다.

**해결 방식은 원인과 무관하게 정해진다** — 스케줄러를 GHA `schedule` 밖으로 옮기면 두 경로가 함께 사라진다. 분 오프셋 같은 GHA 안에서의 조정은 효과를 측정해야만 알 수 있고, 측정에 며칠이 걸리며, 비활성화 위험은 남는다.

## 고려한 선택지

### 선택지 A: GHA 유지 + 정시 회피 (`'17 * * * *'`)

- 장점: 한 줄 변경. 새 서비스 0.
- 단점: best-effort 특성은 그대로다. 정시 혼잡만 피할 뿐 회차 누락이 얼마나 줄지 알 수 없다.
- 단점: 60일 비활성화 위험이 남는다. 1인 프로젝트는 활동 공백이 생기기 쉽다.

### 선택지 B: Vercel Cron

- 장점: 호스팅 안에서 닫혀 외부 인증 경계가 사라진다.
- 단점: **Hobby 플랜은 여전히 하루 1회만 가능**하다(`0 * * * *`는 배포가 거부됨). 같은 1시간 창 안에서도 실행 시각이 흔들린다. ADR 004의 배제 사유가 그대로 유효하다.

### 선택지 C: 외부 cron 서비스 (cron-job.org) (채택)

정해진 시각에 URL을 HTTP로 호출하는 전용 서비스. 지금 GHA가 하는 일(`curl` 한 번)을 그대로 대신한다.

- 장점: 무료, 분 단위 스케줄, 임의 요청 헤더 지원 → **`Authorization: Bearer $CRON_SECRET`을 그대로 쓸 수 있어 서버 코드 변경 0**.
- 장점: 실행 이력(상태 코드·응답 본문)을 보여 주고 **실패 시 이메일 알림**이 있다. #102의 본질이 "조용히 덜 돈다"였으므로 새 스케줄러에서 가장 중요한 성질이 이것이다.
- 장점: ADR 004가 중시한 이식성(호스팅이 바뀌어도 URL만 바꾸면 됨)이 유지된다.
- 단점: 외부 의존이 하나 늘고, `CRON_SECRET`을 제3자 서비스에 맡긴다. 유출 시 피해는 "크롤을 임의로 더 자주 돌릴 수 있다"에 그친다(쓰기 대상은 공개 공고 데이터, 중복 감지는 `last_board_id`가 막음). 회전 절차는 ADR 004와 같다(양쪽 동시 갱신).
- 단점: 요청 타임아웃이 짧다(30초로 알려짐, 공식 확인 필요). 평소 실행은 10~25초지만, 신규 공고가 여럿이라 상세 보강·알림 발송이 길어지면 넘을 수 있다. 아래 "결과"에서 다룬다.

### 선택지 D: Supabase `pg_cron` + `pg_net`

ADR 004는 Supabase 쪽 스케줄링을 "크롤 본체를 Edge Function으로 재구현해야 한다"는 이유로 배제했다. `pg_net`으로 기존 엔드포인트를 HTTP 호출하면 재구현이 필요 없으므로 그 배제 사유는 더 이상 성립하지 않는다.

- 장점: 새 서비스 0. 이미 쓰는 Supabase 프로젝트 안에서 끝난다. 시크릿은 Vault에 둔다.
- 단점: `pg_net`은 비동기 호출이라 실패를 보려면 `net._http_response`를 직접 조회해야 한다. 실패 알림이 기본으로 없다 — #102와 같은 "조용한 실패"를 다시 만들 위험이 C보다 크다.
- 단점: 스케줄이 DB 마이그레이션·대시보드에 들어가 워크플로·README에서 보이지 않는다.

## 결정

크롤 트리거를 **cron-job.org의 매시 호출**로 옮기고, GHA `crawl.yml`에서 `schedule`을 제거한다. GHA는 `workflow_dispatch`(수동 실행) 전용으로 남긴다.

## 근거

- **실패 가시성이 1순위다.** 현 문제는 실행 누락이 아무 신호 없이 일어난 것이다. C는 실행 이력과 실패 이메일을 기본 제공한다. D는 같은 신호를 직접 만들어야 한다.
- **변경 범위가 가장 작다.** 엔드포인트·인증·응답 계약이 그대로라 서버 코드와 테스트가 바뀌지 않는다. 바뀌는 것은 "누가 호출하는가" 하나다.
- **D는 차선책으로 남긴다.** C가 관찰 기간에 기준(아래)을 못 맞추면 D로 간다. 두 선택지 모두 같은 엔드포인트를 부르므로 전환 비용이 작다.

## 결과

### 트리거는 하나만 둔다

라우트는 `last_board_id`를 읽고 → 크롤 → 갱신하는 구조이고, 서버 측 잠금이 없다. 동시 실행 방지는 지금까지 GHA의 `concurrency: crawl` 그룹이 맡았는데, **외부 스케줄러 호출은 이 그룹 밖에 있다.** 두 트리거가 같은 순간에 돌면 둘 다 같은 공고를 신규로 판정해 **알림이 중복 발송**된다. GHA 실행 시각은 지연 때문에 분이 일정하지 않아 오프셋으로 피할 수 없다.

따라서 전환 순서는 다음과 같다.

1. cron-job.org 작업 등록 → 첫 1~2회 실행을 확인한다(이력의 HTTP 200·응답 JSON, 같은 시각에 GHA 실행 없음). 실패하면 GHA가 계속 돌고 있으므로 공백은 없다.
2. 확인 즉시 `schedule` 제거 PR을 머지한다. 두 트리거가 공존하는 시간을 몇 시간 이내로 줄인다.
3. 이후 수동 실행(`workflow_dispatch`)은 cron-job.org 실행 시각과 겹치지 않게 쓴다. `concurrency` 그룹은 수동 실행끼리만 막는다.

### 관찰 기준

머지 후 며칠간 cron-job.org 이력으로 **하루 약 24회, 간격 약 1시간**을 확인한다. 충족 시 #102를 닫고 상태를 "수락됨"으로 바꾼다. 미충족 시 선택지 D로 간다.

### 타임아웃

cron-job.org가 응답을 기다리다 타임아웃해도 실행 이력에 실패로 남아 알 수 있다. 다만 요청이 끊긴 뒤 Vercel 함수가 끝까지 실행되는지는 확인되지 않았다. 중간에 끊기면 저장 후 `last_board_id` 갱신 전에 멈춰 다음 회차가 같은 공고를 다시 처리할 수 있다. 관찰 기간에 신규 공고가 있는 회차의 소요 시간을 확인하고, 문제가 되면 응답을 먼저 반환하고 나머지를 이어서 처리하는 방식(`after()`)을 별도 이슈로 검토한다.

### 문서·설정

- `.github/workflows/crawl.yml`: `schedule` 블록 제거, `workflow_dispatch`·`concurrency` 유지.
- `src/app/api/cron/crawl/route.ts` 상단 주석의 호출자, `README.md` 스케줄러 설명, `.env.example`의 `CRON_SECRET` 주석을 갱신한다.
- `docs/learning/step8-gha-cron-vercel-trigger.md`는 본문을 유지하고 운영 스케줄이 이 ADR로 이전됐다는 포인터만 단다.
- `CRON_SECRET`은 이제 Vercel·GitHub Secrets(수동 실행용)·cron-job.org 세 곳에 있다. 회전 시 세 곳을 함께 갱신한다.
