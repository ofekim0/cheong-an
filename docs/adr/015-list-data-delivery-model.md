# ADR 015: 공고 목록 데이터 전달 모델 — static shell 임베드와 클라이언트 필터링

- **상태**: 제안됨
- **작성일**: 2026-09-04
- **관련 이슈**: #106
- **관련 ADR**: 013 (Cache Components 전환 — 이 ADR이 그중 "쿼리 조합별 캐시" 모델과 세부 판단 1을 대체한다. 플래그·태그 무효화·`{ expire: 0 }`는 유지), 001 (TanStack Query 용도)
- **대체 대상**: ADR 013 세부 판단 1(`'use cache: remote'`) 및 "조회 결과는 쿼리 조합별로 캐시된다"는 모델

## 맥락

Step c(ADR 013)는 목록 페이지를 Cache Components로 전환하면서 **필터 조건마다 서버가 결과를 만든다**는 전제를 두었다. `searchParams`를 Suspense 하위에서 읽고, (page, filters)를 키로 `'use cache: remote'`에 담고, 크롤이 태그로 무효화한다. 이 모델은 DB 조회 수를 끊는 데는 성공했지만(웜 히트 확인, ADR 013 "캐시 적중 검증"), 사용자 체감에는 세 겹의 지연이 남았다.

1. **클릭 피드백이 서버에 있다.** `AnnouncementFilterBar`가 Suspense 경계 안의 서버 컴포넌트라 "어느 칩이 선택됐는가"조차 서버 응답으로 온다. React transition은 기존 화면을 유지하므로 응답이 오기까지 클릭이 씹힌 것처럼 보인다.
2. **클릭마다 서버 왕복이 필수다.** 목록이 `searchParams` 뒤에 있어 요청 시점에만 렌더된다. `Link` prefetch는 static shell만 미리 받는데 그 shell은 이미 화면에 있는 것과 같아 얻는 것이 없다.
3. **왕복 자체가 짧지 않다.** 캐시 히트여도 브라우저 → Vercel 함수 → remote 캐시 저장소 → 회신이 0.33~0.37초다(ADR 013 측정). 콜드는 최대 1.0초. 크롤이 1시간마다 태그를 통째로 무효화하므로 크롤 직후 첫 방문자는 조합마다 콜드를 맞는다.

그런데 이 서비스의 데이터는 **크롤 주기(1시간)로만 바뀌고, 전체가 69건**이다. 요약 컬럼 8개로 전량을 실어도 20KB 안팎이다. 필터 조건마다 서버가 잘라 줄 이유가 없다 — 전체를 한 번 내려보내고 브라우저가 고르면 1·2·3이 동시에 사라진다. ADR 013의 선택지 표에는 이 축이 없었다. 검토 후 기각된 것이 아니라 검토되지 않았다 — Step b가 서버 페이지네이션 20건으로 시작했고 필터가 그 위에 얹혀 "서버가 자른다"가 자연스럽게 이어졌다.

## 고려한 선택지

### 선택지 1: 현행 유지 + 낙관적 UI

서버 모델은 그대로 두고, 필터 바만 클라이언트로 바꿔 선택 상태를 즉시 표시하고 `useLinkStatus`/`useTransition`의 pending으로 목록에 로딩 표시를 넣는다.

- 장점: 변경이 UI 한 컴포넌트로 국한된다. 캐시·무효화 코드 무변경.
- 장점: 지연 1(피드백 부재)은 해소된다.
- 단점: 지연 2·3은 그대로다. 클릭마다 0.33~1.0초를 여전히 기다리고, 로딩 표시가 그 기다림을 눈에 보이게 만들 뿐이다.
- 단점: 필터 차원이 늘수록 캐시 항목 수가 곱으로 늘고 콜드 비율이 오른다. 구조적 부채가 남는다.

### 선택지 2: 전량을 static shell에 임베드 + 클라이언트 필터링 (채택)

전량 조회를 `searchParams` **앞**으로 옮겨 `'use cache'` + 태그로 감싼다. 요청 시점 값을 읽지 않으므로 결과가 static shell(빌드 산출물)에 들어가고, 태그 무효화 시 다시 만들어진다. 필터·페이지 계산은 `useSearchParams`를 읽는 클라이언트 컴포넌트가 배열 위에서 한다. 필터·페이지 링크는 `href`를 유지하되 클릭 시 `history.pushState`로 URL만 바꾼다.

- 장점: 지연 1·2·3이 모두 사라진다. 클릭 반응은 로컬 배열 연산이고 서버 요청은 0건이다.
- 장점: 캐시 항목이 조합 수와 무관하게 **1개**다. 콜드 미스라는 개념이 사실상 사라진다(빌드 또는 태그 무효화 직후 1회).
- 장점: 필터 차원이 늘어도 서버·캐시 무변경. 지역·정렬·검색어를 붙여도 브라우저 계산이다.
- 장점: `count: 'exact'`, 범위 초과 fallback count, `PGRST103` 처리, `applyFilters`가 전부 불필요해져 리포지터리가 줄어든다.
- 장점: URL이 상태라는 원칙, 태그 무효화, 서버 전용 DB 접근(anon GRANT 없음)은 그대로다. 기존 북마크가 동작한다.
- 단점: **데이터 크기가 첫 로드 크기가 된다.** 상한을 정해야 한다(아래 "결과 — 성장 트리거").
- 단점: 목록 페이지에 JS가 생긴다(클라이언트 컴포넌트 1개 + pushState 핸들러). c-3의 "JS 0" 기록은 사실이 아니게 된다.
- 단점: 빌드가 실제로 DB를 읽는다. CI `pnpm build`에 Supabase 자격 증명이 필요해진다.
- 단점: `?type=public`으로 직접 진입하면 shell은 URL을 모르므로 목록 자리에 자리표시자가 한 프레임 보인 뒤 하이드레이션 직후 필터된 목록이 뜬다. 서버 왕복은 없다. 현행(0.3~1.0초 스켈레톤)보다 나빠지지 않는다.

### 선택지 3: 크롤 시 스냅샷 JSON 생성 + 브라우저 fetch

크롤 라우트가 저장 직후 연도별 요약 JSON과 메타(필터별 건수)를 정적 자산으로 내보내고, 브라우저가 TanStack Query로 청크를 가져와 필터링한다. 최근 청크는 shell에 임베드, 과거 청크는 지연 로드.

- 장점: 데이터가 수천 건이 되어도 첫 로드 크기가 고정된다. 선택지 2의 유일한 구조적 단점을 해소한다.
- 장점: ADR 001이 TanStack Query에 부여한 용도("공고 데이터 캐싱, 백그라운드 리프레시")와 정확히 맞는 첫 소비자가 된다.
- 단점: 지금 규모에서 필요가 없고, **올바르게 설계할 정보도 없다.** 청크 경계(연도별인지 최근 12개월인지, 상한이 얼마인지)는 실제 증가 속도와 과거 공고 열람 비율에 달려 있는데 둘 다 측정된 바 없다.
- 단점: 실패 지점이 늘어난다 — 청크 일부만 도착한 상태의 표시, 메타 집계와 청크 내용의 불일치, 크롤 도중 청크·메타가 어긋나는 순간. 지금 규모에서는 재현조차 안 되어 검증이 어렵다.
- 단점: 크롤 라우트에 스냅샷 생성 단계가 붙어 크롤의 실패 표면이 넓어진다.

## 결정

목록 페이지를 **선택지 2**로 전환한다. 전량 요약을 `'use cache'` + `cacheTag(ANNOUNCEMENTS_CACHE_TAG)`로 static shell에 임베드하고, 필터·페이지네이션은 `useSearchParams`를 읽는 클라이언트 컴포넌트가 로컬에서 계산하며, 링크는 `href` 유지 + `history.pushState`로 서버 요청 없이 URL을 바꾼다. 선택지 3은 아래 성장 트리거가 켜질 때 선택지 2 위에 **한 층 더 얹는** 방식으로 진행한다.

## 근거

선택지 1은 증상만 가린다. 사용자가 기다리는 시간은 그대로고 기다림이 보이게 될 뿐이다. 이 서비스에서 서버 왕복이 필요한 이유가 "필터 조건마다 서버가 잘라야 한다"인데, 그 전제 자체가 데이터 성격(주기 갱신, 소량)과 맞지 않는다. 전제를 고치지 않고 UI를 고치는 것은 순서가 틀렸다.

선택지 3은 선택지 2가 커진 뒤의 모습이지 대안이 아니다. 지금 넣으면 쓰이지 않는 코드 경로가 프로덕션에 존재하고 테스트로만 살아 있게 된다. 선택지 2를 **1·3층(상호작용·순수 로직)은 그대로 두고 2층(데이터 공급원)만 바뀌게** 짜두면, 미루는 대가가 "다시 짠다"가 아니라 "한 층 얹는다"가 된다. 그래서 미룰 수 있다.

### 세부 판단 1: `'use cache: remote'`가 아니라 `'use cache'`

ADR 013이 remote를 택한 근거는 "조회가 `searchParams` 뒤에 있어 요청 시점으로 밀린다"였다. 이 조건이 사라진다. 조회가 요청 시점 값 앞에 있으면 결과는 static shell의 일부가 되어 빌드 산출물로 CDN에서 나간다. 함수 인스턴스의 인메모리 공유 문제가 성립하지 않는다. 태그 무효화(`revalidateTag(tag, { expire: 0 })`)는 그대로 동작하며, 이때 shell이 재생성된다. 세부 판단 2·3(`{ expire: 0 }`, 세그먼트 설정 제거)은 ADR 013 그대로 유효하다.

### 세부 판단 2: 링크는 `href` 유지 + `history.pushState`

`Link`의 기본 네비게이션에 맡기면 같은 라우트의 쿼리 변경에도 라우터가 RSC 페이로드를 다시 요청할 수 있다(CDN 히트라 빠르지만 0은 아니다). Next가 공식 지원하는 shallow routing — `window.history.pushState`를 직접 호출하면 라우터가 이를 감지해 `useSearchParams`를 갱신하고 서버 요청은 발생하지 않는다 — 을 쓴다. `href`를 남기는 이유는 둘이다: JS가 꺼져도 전체 로드로 동작하고, 새 탭 열기·링크 복사 같은 브라우저 기본 동작이 유지된다. `<button>`으로 바꾸면 둘 다 잃는다.

### 세부 판단 3: 파싱 규칙은 재사용, 계산은 순수 함수로 분리

`parseListParams`의 규칙(화이트리스트, 배열은 첫 값, 잘못된 page는 1)은 입력이 `searchParams` 객체에서 `URLSearchParams`로 바뀔 뿐 그대로다 — 어댑터 하나로 잇는다. 필터·페이지네이션 계산은 `src/lib/announcements/filterAnnouncements.ts`에 순수 함수로 둔다. 컴포넌트가 아닌 모듈로 두는 이유는 `parseListParams`와 같다 — 여기에 실제 분기가 있고, 선택지 3으로 가도 이 함수는 데이터 공급원과 무관하게 그대로 쓰인다.

### 세부 판단 4: CI 빌드에 test 프로젝트 자격 증명을 준다

빌드가 DB를 읽게 되므로 env 없는 `pnpm build`는 실패한다. 두 길 중 자격 증명 주입을 택한다. e2e 워크플로가 이미 쓰는 `TEST_SUPABASE_URL`·`TEST_SUPABASE_SERVICE_ROLE_KEY`를 `ci.yml`의 Build 단계에 넘기면 끝이고, 빌드가 실제 데이터 경로를 검증하게 되어 오히려 이득이다. 다른 길 — env 부재 시 빈 목록 폴백 — 은 ADR 013이 "자격 증명 누락이 '공고 없음'으로 위장된다"며 걷어낸 가드를 되살리는 것이라 배제한다.

### 세부 판단 5: TanStack Query는 이 단계에서 넣지 않는다

ADR 001이 도입을 이미 결정했으므로 여부는 논점이 아니다. 넣지 않는 이유는 **할 일이 없기 때문**이다 — 데이터가 props로 도착하고 fetch·비동기 상태·캐시할 응답이 없다. `initialData`로 props를 감싸는 것은 라이브러리를 쓴 흔적을 남기는 의식이지 ADR 001의 "심화 활용"이 아니다. 첫 소비자는 **브라우저가 처음으로 데이터를 직접 가져오는 순간**에 생기며, 후보는 (a) 열어둔 탭의 백그라운드 리프레시(규모 무관, 이쪽이 먼저 올 가능성이 높다), (b) 선택지 3의 청크 지연 로드다. 도입 시점의 설계는 그때 ADR로 기록한다.

## 배제한 접근 (회귀 방지)

- **필터 바만 클라이언트로 바꾸고 서버 모델 유지(선택지 1)** — 지연 2·3이 남는다. 로딩 표시는 기다림을 없애지 않는다.
- **`'use cache: remote'` 유지** — remote의 근거(요청 시점으로 밀림)가 소멸했다. 남기면 CDN 대신 캐시 저장소 왕복이 매 요청에 붙는다.
- **필터 링크를 `<button>` + 상태로 교체** — JS 없는 동작과 새 탭·링크 복사를 잃는다. `href` + `pushState`가 둘 다 지킨다.
- **`Link` 기본 네비게이션에 맡기기** — 같은 라우트 쿼리 변경에도 RSC 재요청이 발생할 수 있다. 서버 요청 0을 보장하는 것은 `pushState`다.
- **env 부재 시 빈 목록 폴백** — 세부 판단 4. 자격 증명 누락이 에러 대신 "공고 없음"으로 위장된다.
- **지금 청크 분할·TanStack Query 도입(선택지 3 선행)** — 설계할 정보가 없고 쓰이지 않는 경로가 생긴다. 성장 트리거로 시점을 측정에 맡긴다.
- **서버 `listAnnouncements`·`countAnnouncements`·`applyFilters` 잔존** — 호출자가 없다. 남기면 "서버가 자른다" 모델이 되살아나는 입구가 된다. 삭제한다.

## 결과

- **체감 지연 3겹이 사라진다.** 필터·페이지 클릭은 로컬 배열 연산 + `pushState`. 네트워크 요청 0건. **검증됨(2026-09-04, Step b, 로컬 dev 서버 + Playwright 스크립트)**: 초기 로드 후 "공공" → "추가모집" → 유형 "전체" → 2페이지 → 뒤로가기의 다섯 전환에서 websocket을 제외한 네트워크 요청이 **각각 0건**이었다. 건수 문구·선택 칩·`aria-current`가 URL을 따라 즉시 바뀌었고, 페이지 이동 후 `scrollY`는 0이었다. `?type=public&page=1` 직접 진입은 필터된 목록과 선택 칩을 그대로 그렸고, Ctrl/⌘+클릭은 가로채지 않아 새 탭이 열리고 원 탭 URL은 그대로였다.
- **빌드 출력 검증됨(2026-09-04)**: `/announcements`가 `◐`(Partial Prerender)에서 **`○`(Static, Revalidate 1h · Expire 1d)**로 바뀌었다. `useSearchParams` 하위가 클라이언트 렌더로 빠지므로 shell 자체가 완전 정적이다. `/announcements/[boardId]`는 `◐` 그대로다.
- **목록의 캐시 항목이 1개가 된다.** 크롤 무효화 후 첫 방문 1회만 DB를 읽는다. 조합별 콜드 미스가 사라진다. 다만 `ANNOUNCEMENTS_CACHE_TAG`는 상세 페이지(`/announcements/[boardId]`, boardId별 `'use cache: remote'` 항목, #96)도 덮고 있으므로 **태그 무효화의 존재 이유는 그대로다** — 지목해야 할 항목이 "목록 조합들"에서 "목록 1건 + 상세 N건"으로 바뀔 뿐이다. 상세 페이지의 remote 선택은 `params`가 요청 시점 값이라 ADR 013 세부 판단 1의 근거가 여전히 성립하므로 이 ADR의 대체 범위 밖이다.
- **리포지터리가 줄어든다.** `listAnnouncements`·`countAnnouncements`·`applyFilters`·`PGRST103` 처리와 그 테스트를 삭제하고 `listAllAnnouncementSummaries` 하나가 남는다.
- **`/announcements`의 빌드 기호가 바뀔 수 있다.** `◐`(Partial Prerender)에서 `○`(Static)로 — `useSearchParams` 하위가 클라이언트 렌더로 빠지므로 shell 자체는 완전 정적이다. 빌드 출력으로 확인한다.
- **CI가 빌드 시 test DB를 읽는다.** `cheong-an-test`가 pause 상태면 CI 빌드가 깨진다(e2e와 같은 의존). 증상은 DNS `ENOTFOUND`, 조치는 Resume.
- **주석 정정 대상**: `constants/announcements.ts`의 태그 설명, 크롤 라우트의 무효화 주석, 페이지 상단 문서 주석이 "쿼리 조합마다 캐시 항목이 따로 생긴다"를 태그의 근거로 적고 있다. 근거가 "목록 1건 + 상세 boardId별 항목"으로 바뀌므로 함께 고친다. `step83-cache-components.md` §3(디렉티브 선택)에 이 ADR 포인터를 붙인다.
- **선행 조건 — #101(목록 → 상세 E2E)을 먼저 머지한다.** #101이 "ADR 015 전환 전에 회귀 방어가 있으면 안전망이 된다"고 명시했다. 목록 카드 → 상세 이동 스펙이 먼저 있어야 이 전환이 카드 링크를 깨뜨렸는지 CI가 잡는다. 이 ADR의 Step c에 예정한 "필터 클릭 → 건수 변경" 스펙은 #101 스펙과 같은 파일에 추가한다.
- **성장 트리거 (선택지 3으로 넘어가는 조건)**: 아래 둘 중 하나가 깨지면 청크 분할을 시작한다. "언제 하는가"를 판단이 아니라 측정으로 둔다.
  - 첫 로드에 임베드되는 목록 데이터: **압축 후 50KB 이하**
  - 필터·페이지 클릭 반응: **로컬 데이터로 100ms 이내, 네트워크 대기 없음**
- **되돌리는 비용**: 페이지를 ADR 013 형태(`searchParams` Suspense 하위 읽기 + `'use cache: remote'`)로 복원하고 리포지터리의 서버 필터·count를 되살린다. git 이력에 있어 기계적이지만, 되돌리는 순간 체감 지연 3겹도 되돌아온다.
- **작업 분할**: Step a(순수 로직 + `listAll` + 테스트) → b(페이지·클라이언트 전환, `pushState`, CI env, 이 ADR) → c(구 조회 경로 삭제, 주석 정정, e2e 1건, 학습 문서). 각 Step은 독립 머지 가능.
