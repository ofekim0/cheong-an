# ADR 018: UI 디자인 품질 검증 — Impeccable 도입

- **상태**: 제안됨
- **작성일**: 2026-11-27
- **관련 이슈**: #114
- **관련 ADR**: 016 (shadcn/ui 도입 — #111 UI 디자인 일괄 적용의 컴포넌트 기반)

## 맥락

#111(UI 디자인 일괄 적용)은 v0로 4개 화면을 **생성**하고 Step a~d로 이식하는 계획이다(`docs/design/v0-prompt.md`, ADR 016). 생성 쪽 도구는 정해졌지만, 결과물을 **검증**할 수단이 없다.

- v0 프롬프트는 "텍스트 대비 WCAG AA 이상", "선택 상태는 색만이 아니라 형태로도 구분" 같은 요구를 걸어 두었지만, 이식된 화면이 그것을 지켰는지 확인하는 절차가 없다. 지금은 눈으로 본다.
- 기존 린트(`eslint-config-next/core-web-vitals`)에 포함된 `jsx-a11y` 규칙은 `alt` 누락 같은 마크업 수준만 본다. 렌더 결과의 대비, 글자 크기, 타입 위계, 간격은 보지 않는다.
- 1인 프로젝트라 디자인 리뷰어가 없다. 코딩 에이전트에게 UI를 맡기면 흔한 기본값(Inter, 보라 그라데이션, 카드 중첩 등)으로 수렴하는 경향이 있는데, 이를 걸러낼 기준도 없다.

[Impeccable](https://github.com/pbakaus/impeccable)(v4.11.1, Apache 2.0)은 이 공백을 겨냥한 도구다. 세 부분으로 되어 있다.

1. **결정론적 검출기**: `npx impeccable detect`. LLM 없이 규칙 62개로 판정한다. 소스 파일은 정규식 규칙만 보고, URL을 주면 렌더된 페이지에서 대비·글자 크기 등 요소 규칙까지 돈다. `--sarif`/`--github` 출력으로 CI에 붙일 수 있다.
2. **에이전트 스킬**: `/impeccable critique`(사용성 휴리스틱 점수), `audit`(접근성·성능·반응형, P0~P3), `polish`·`harden` 등 대상을 좁혀 실행하는 명령. `PRODUCT.md`(제품 맥락)와 `DESIGN.md`(시각 체계)를 읽고 동작한다.
3. **디자인 훅**: 에이전트가 UI 파일을 편집할 때마다 검출기를 자동 실행한다.

도입 전 시범 실행(2026-11-27, 설치 없이 `npx`) 결과:

| 대상                                            | 결과                                                                                                                                                                           |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 소스(`src/`, 99개 파일)                         | `globals.css`의 `body { font-family: Arial }`이 `next/font`로 로드한 Geist를 덮어씀 → Geist는 다운로드만 되고 미사용. 나머지 2건은 크롤러 픽스처(외부 사이트 원본 HTML) 노이즈 |
| 렌더(`/`, `/announcements`, `/subscribe`, 상세) | 페이지네이션 비활성 "이전/다음" 대비 1.5:1 1건. WCAG 1.4.3상 비활성 컴포넌트 예외라 위반은 아님                                                                                |

사람이 놓친 실제 결함(폰트 덮어쓰기)을 1건 잡았고, 오탐은 경로 제외와 판단으로 처리 가능한 수준이었다.

## 고려한 선택지

### 선택지 A: 도구 없이 수동 검토 유지

- 장점: 추가 의존 0.
- 단점: #111 이식 후 v0 프롬프트의 접근성 요구를 지켰는지 확인할 근거가 남지 않는다. 폰트 덮어쓰기처럼 눈에 띄지 않는 결함은 계속 놓친다.

### 선택지 B: 범용 접근성 도구 (axe-core, Lighthouse CI)

- 장점: 업계 표준. 접근성 규칙의 폭과 신뢰도가 높다.
- 단점: 접근성만 본다. 타입 위계, 간격, 흔한 기본값 수렴 같은 디자인 품질은 범위 밖이고, `critique`처럼 개선 우선순위를 내주는 리뷰 기능이 없다.
- 단점: E2E나 CI에 러너를 새로 붙여야 해서 시범 비용이 Impeccable(`npx` 한 줄)보다 크다.

### 선택지 C: Impeccable 전면 도입 (스킬 커밋 + 훅 + CI 게이트)

- 장점: 에이전트 편집마다 자동 검사, PR마다 신규 위반 차단까지 한 번에 갖춘다.
- 단점: 설치 산출물(스킬 본체·레퍼런스·런처·서브에이전트 68개 파일, `live-browser.js` 약 560KB)이 저장소에 들어간다. `impeccable update` 때마다 수십 개 파일의 diff가 생긴다.
- 단점: 훅은 모델 승인과 별개로 실행되고 첫 실행 때 엔진 바이너리를 내려받는다. 도구의 쓸모를 확인하기 전에 자동 실행부터 거는 셈이다.
- 단점: 현재 UI는 #111로 곧 교체된다. 지금 CI 게이트를 걸면 버려질 화면의 위반을 관리하게 된다.

### 선택지 D: Impeccable을 검증 도구로 단계적 도입 (채택)

프로젝트 범위로 설치하되 산출물은 커밋하지 않고, 훅과 CI는 보류한다. 수동 `detect`와 `critique`/`audit`로 시작한다.

- 장점: 시범 비용이 작고, 쓸모가 확인된 기능만 다음 단계로 올린다.
- 장점: #111의 검증 수단으로 바로 쓸 수 있다. 생성(v0)과 검증(Impeccable)의 역할이 겹치지 않는다.
- 단점: 설치가 각 환경에서 재현되어야 한다(`npx impeccable install` 한 줄이라 1인 프로젝트에서는 부담이 작다).
- 단점: 자동 실행이 없으므로 검사를 잊을 수 있다. 아래 "결과"의 승격 조건으로 다룬다.

## 결정

Impeccable을 **UI 검증 도구로** 프로젝트에 설치하고, 설치 산출물은 커밋하지 않으며, 디자인 훅과 CI 게이트는 #111 이식 이후로 보류한다.

## 근거

- **생성과 검증을 분리한다.** #111은 v0가 디자인을 만들고 ADR 016의 shadcn/ui가 컴포넌트 기반을 맡는다. Impeccable은 그 결과를 재는 자 역할만 한다. 디자인을 새로 만드는 명령(`bolder`, `overdrive`, `live` 등)은 #111의 v0 경로와 겹치므로 쓰지 않는다.
- **검증 범위가 B보다 넓다.** 대비·글자 크기 같은 접근성 규칙에 더해 타입 위계, 폰트 설정, 흔한 기본값 수렴까지 본다. 시범 실행에서 잡은 폰트 덮어쓰기는 B의 범위 밖이다.
- **설치 산출물은 외부 도구의 배포물이다.** 청안 코드가 아니고 한 줄로 재생성되므로, `.eslintrc`처럼 프로젝트 고유 설정(`.impeccable/config.json`)만 커밋하고 본체는 `node_modules`처럼 취급한다.
- **자동화는 대상이 안정된 뒤에 건다.** 현재 화면은 흐름 검증용 최소 UI라 #111에서 교체된다. 지금 훅과 CI를 걸면 교체될 화면의 위반을 관리하는 비용만 생긴다.

## 결과

### 지금 반영한 것 (#114)

- `.gitignore`: `.claude/skills/impeccable/`, `.claude/agents/impeccable-*.md`(설치 산출물)와 Impeccable README의 `impeccable-ignore` 블록(캐시·스크린샷·live 런타임 상태). 공유 산출물(`config.json`, `design.json`, `surfaces/*.md` 등)은 추적된다.
- `.impeccable/config.json`: `detector.ignoreFiles`에 `src/lib/crawler/__fixtures__/**`. 파서 테스트용 외부 사이트 원본 HTML이라 청안이 고칠 대상이 아니다.
- 재설치: `npx impeccable install --providers=claude --scope=project`. 훅 질문에는 `n`(거절 기록은 `.impeccable/config.local.json`, 커밋 안 함).

### #111과의 순서

- **`PRODUCT.md`는 지금 작성해도 된다.** 대상 사용자, 목적, 제약은 디자인 교체와 무관하다.
- **`DESIGN.md`는 #111 Step a(토큰·Pretendard·레이아웃) 머지 후에 작성한다.** 지금 `/impeccable document`를 돌리면 교체될 Next.js 템플릿 기본값(Geist, `#171717` 등)을 디자인 시스템으로 기록하게 된다.
- **시범 실행의 폰트 결함은 따로 고치지 않는다.** #111 Step a에서 Pretendard를 `next/font/local`로 주입하면서 `globals.css`의 `body` 폰트 선언을 정리하면 함께 해결된다. Step a 검증 항목에 넣는다.
- #111 각 Step 이식 후 렌더 스캔(`detect http://localhost:3000/...`)과 해당 화면의 `critique`/`audit`를 돌려 v0 프롬프트의 접근성 요구를 확인한다.

### 승격 조건

- **CI 게이트**(`detect --sarif` → code scanning): #111 Step d까지 머지되고 렌더 스캔이 깨끗해진 뒤. PR에서 새로 생긴 위반만 실패로 처리되므로 기존 위반이 남아 있어도 걸 수는 있지만, 교체 중인 화면을 기준선으로 삼을 이유가 없다.
- **디자인 훅**: 에이전트에게 UI 편집을 맡기는 빈도가 늘어 수동 `detect`를 잊는 일이 생기면 켠다(`/impeccable hooks on`).

### 주의 사항

- **텔레메트리**: 새 디자인 시작 시 고른 시각 방향을 익명으로 전송한다(코드·파일·`PRODUCT.md`는 전송하지 않는다고 명시). 이 ADR의 사용 범위(검증)에서는 해당 흐름을 거의 타지 않지만, 끄려면 `.impeccable/config.json`에 `"telemetry": false`.
- **`live` 모드는 쓰지 않는다.** Apply 시 채팅 세션이 없으면 `codex`/`claude` CLI를 권한 우회 모드로 실행한다. 쓰게 되면 `IMPECCABLE_LIVE_COPY_AGENT=chat`을 먼저 설정한다.
- **Windows에서 렌더 스캔용 dev 서버는 PowerShell(`C:\...` 경로)에서 띄운다.** Git Bash(`/c/...`)에서 `pnpm dev`를 띄우면 Turbopack이 모든 경로를 404로 응답했다(2026-11-27 확인).
- **판정은 근거이지 결론이 아니다.** 비활성 컴포넌트의 대비처럼 WCAG 예외에 해당하는 검출이 있다. 예외로 판단한 항목은 `npx impeccable ignores add-value` 또는 인라인 주석에 사유를 남기고, `--report-unused-ignores`로 낡은 예외를 정리한다.
- **되돌리기**: `.claude/skills/impeccable/`, `.claude/agents/impeccable-*.md`, `.impeccable/`을 지우고 `.gitignore` 블록을 제거하면 끝난다. 앱 코드와 의존성(`package.json`)에는 아무것도 추가되지 않았다.
