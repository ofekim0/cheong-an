# ADR 016: UI 컴포넌트 기반 — shadcn/ui 도입

- **상태**: 제안됨
- **작성일**: 2026-09-07
- **관련 이슈**: #111
- **관련 ADR**: 001 (기술 스택 — Tailwind CSS 선택), 013 (Cache Components — 표시 컴포넌트를 서버 컴포넌트로 유지하는 제약)

## 맥락

Sprint 2 마지막 항목인 UI 디자인 일괄 적용(#111)을 v0로 진행한다. 현재 화면 4개(홈·목록·상세·구독)는 흐름 검증용 최소 UI라 배지·칩·토글·스켈레톤을 각 파일 안에서 Tailwind 유틸리티 문자열로 직접 그리고 있다. 공통 컴포넌트가 없어 같은 배지가 목록 카드와 상세 페이지에 두 번 정의되어 있다.

디자인을 입히는 시점에 두 가지가 겹친다.

1. **v0의 기본 출력은 shadcn/ui다.** 프롬프트로 배제할 수는 있지만, 배제하면 결과 편차가 커지고 생성된 코드에서 Radix·cva 의존을 걷어내 다시 쓰는 이식 비용이 생긴다.
2. **Sprint 3에 상호작용 컴포넌트가 늘어난다.** 지역구 필터는 서울 25개 자치구 다중 선택이고, 공고 유형 필터·조건부 알림 설정이 구독 페이지에 붙는다. 체크박스 그룹 또는 콤보박스, 폼 상태 표시가 필요해지며, 키보드 탐색과 스크린리더 대응을 직접 구현하면 비용이 크다.

지금 도입하지 않으면 이번에 만든 토글·배지·토큰을 Sprint 3에서 shadcn 체계로 한 번 더 고치게 된다. 도입 시점을 정하는 것이 이 ADR의 문제다.

## 고려한 선택지

### 선택지 1: 순수 Tailwind 유지, 라이브러리 미도입

배지·칩·토글·스켈레톤을 `components/ui/`에 자체 컴포넌트로 추출하고, 접근성은 직접 구현한다.

- 장점: 의존성 추가 0. 현재 화면 규모(상호작용 요소는 토글 2개와 링크 칩)에서는 충분하다.
- 장점: 번들에 Radix 런타임이 들어가지 않는다.
- 단점: v0 출력을 그대로 못 쓴다. shadcn 컴포넌트 참조를 전부 자체 구현으로 치환해야 한다.
- 단점: Sprint 3의 다중 선택·콤보박스에서 접근성(roving tabindex, aria-selected, 포커스 관리)을 손으로 짜야 한다. 그 시점에 결국 라이브러리를 도입하면 이번 작업이 이중이 된다.

### 선택지 2: shadcn/ui 도입, Step a에서 초기화 (채택)

`shadcn init`으로 `components.json`과 토큰 CSS 변수를 설정하고, 필요한 컴포넌트만 `components/ui/`에 추가한다. v0 출력을 거의 그대로 이식한다.

- 장점: v0 결과물과 프로젝트 구조가 일치해 이식이 `className`·마크업 복사 수준으로 줄어든다.
- 장점: 컴포넌트가 프로젝트 안으로 복사되므로 소스를 소유한다. 업스트림 업데이트에 끌려가지 않고, 필요하면 자유롭게 고친다.
- 장점: Radix 기반이라 Sprint 3의 다중 선택·콤보박스·토글이 접근성 처리된 상태로 온다.
- 장점: 토큰 체계(`--primary`, `--muted`, `--border` 등 역할 기반 CSS 변수)가 표준화되어 있어 v0의 후속 수정 요청과 우리 코드가 같은 어휘를 쓴다.
- 단점: 의존성 추가 — `radix-ui`(또는 `@radix-ui/*` 개별), `class-variance-authority`, `lucide-react`, `tw-animate-css`. 사용하는 컴포넌트만큼만 늘어난다.
- 단점: `components/ui/`에 복사된 코드는 우리 컨벤션(주석·네이밍)과 다를 수 있다. 수정하지 않고 두는 것을 원칙으로 한다(아래 "결과").

### 선택지 3: 다른 컴포넌트 라이브러리 (Radix Themes, Mantine, Chakra 등)

- 장점: 완성된 디자인 시스템을 바로 쓴다.
- 단점: 런타임 CSS-in-JS 또는 자체 테마 엔진이 Tailwind와 이중이 되고, 서버 컴포넌트 호환이 제한적인 경우가 있다(ADR 013 제약과 충돌).
- 단점: v0 출력과 무관해 이식 이점이 없다. 검토 대상으로만 기록한다.

### 선택지 4: shadcn/ui 도입을 Sprint 3으로 연기

이번에는 선택지 1로 가고, 지역구 필터 시점에 도입한다.

- 장점: Step a 범위가 작다.
- 단점: 이번에 만든 토글·배지·토큰을 Sprint 3에서 다시 만든다. ADR은 어느 시점이든 1건이라 절약되는 것이 없다. v0 이식 비용은 이번에 그대로 지불한다.

## 결정

shadcn/ui를 도입하고, #111 Step a에서 초기화한다. 컴포넌트는 실제 사용하는 것만 추가한다.

## 근거

비용 비교에서 선택지 2가 선택지 4보다 작업 총량이 적다. 도입 가능성이 높은 것을 미루면 같은 컴포넌트를 두 번 작성하게 되고, 미룸으로써 얻는 것은 Step a 범위 축소뿐이다. 선택지 1은 Sprint 3에서 접근성 구현 비용이 크고, 그 비용이 청안의 학습 목표(상태 관리·시각화·성능)와 겹치지 않는다.

기존 스택과의 정합성도 확인했다.

- Tailwind v4: shadcn/ui는 v4를 지원하며 토큰을 `@theme inline`으로 선언한다. 현재 `globals.css`가 이미 그 패턴이다.
- `cn()`: 프로젝트에 `clsx` + `tailwind-merge` 조합의 `src/lib/utils/cn.ts`가 있다. `components.json`의 `aliases.utils`를 여기로 지정하면 중복 유틸이 생기지 않는다.
- 서버 컴포넌트(ADR 013): Badge·Skeleton·Button(링크 용도)은 클라이언트 상태가 없어 서버 컴포넌트에서 쓸 수 있다. Switch는 Radix 상태를 가져 클라이언트 컴포넌트지만, 현재 토글 버튼도 이미 클라이언트 컴포넌트다.
- 폴더 구조: 복사되는 위치 `src/components/ui/`는 CLAUDE.md의 "범용 UI 컴포넌트" 위치와 같다.
- React 19 / Next.js 16: 지원 범위다.

## 결과

- **의존성**: 컴포넌트가 요구하는 만큼만 추가한다. Step a 시점 예상은 Button·Badge·Switch·Skeleton 4개다. 추가할 때마다 PR 본문에 어떤 컴포넌트를 왜 넣었는지 적는다.
- **`components/ui/` 수정 원칙**: shadcn이 복사한 파일은 가능한 한 그대로 둔다. 스타일 변형은 `variant` 추가로, 동작 변경이 필요하면 감싸는 컴포넌트를 `components/[feature]/`에 만든다. 이 원칙은 CLI로 컴포넌트를 재추가(덮어쓰기)할 수 있는 여지를 남기기 위한 것이다.
- **테스트**: `components/ui/` 자체는 테스트하지 않는다(외부 라이브러리 동작 — 테스트 원칙). 이를 조합한 기능 컴포넌트와 E2E는 기존 원칙대로다.
- **번들 크기**: Radix 런타임이 들어간다. Sprint 5 번들 분석 시 `@radix-ui` 비중을 측정 항목에 넣는다. 사용하지 않는 컴포넌트를 깔아 두지 않는 것이 1차 방어다.
- **Sprint 3 영향**: 지역구 다중 선택은 shadcn의 Checkbox 또는 Command(콤보박스)로 시작한다. 이 ADR이 그 선택을 미리 정하지는 않는다.
- **되돌리기**: 컴포넌트가 소스로 존재하므로, 도입을 철회해도 파일은 남고 의존성만 제거하면 된다. Radix를 자체 구현으로 대체하는 비용은 컴포넌트 수에 비례한다.
