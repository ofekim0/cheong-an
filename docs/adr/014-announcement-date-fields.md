# ADR 014: 공고 날짜 필드 정정 — 필드명 리네임과 부재 필드 제거

- **상태**: 제안됨
- **작성일**: 2026-09-03
- **관련 이슈**: #86 (Step b), 배경: #83 (Step b 브라우저 검증)
- **관련 ADR**: 003 (저장 매핑 — 옵션 B), 012 (목록 파서 row 격리)

## 맥락

#83 Step b(공고 목록 페이지)의 브라우저 검증에서 전 카드가 `모집 ○○ ~ 미정`으로 표시됐다. 추적 결과 DB 68건 전부 `application_end_date`·`result_date`가 null이었고, 원인은 파서 버그가 아니라 **소스에 그 데이터가 없기 때문**이었다. 원본 view.do(boardId 6644) 메타 영역(`ul.view_data`)이 노출하는 날짜 항목은 **'공고게시일'과 '청약신청일' 둘뿐**이고, '모집 마감일'·'발표일' 항목은 존재하지 않는다.

여기서 세 갈래의 어긋남이 나왔다.

1. **`parseListJson`의 매핑이 틀렸다** — `optn1`(공고게시일)을 `applicationStartDate`로, `optn4`(청약신청일)를 `applicationEndDate`로 넣었다. → **Step a(PR #93)에서 정정 완료.** 이 ADR의 대상이 아니다.
2. **필드명이 값의 의미와 어긋난다** — `parseDetailPage`는 '청약신청일'을 `applicationStartDate`에 담는다. 값은 맞지만 이름은 "모집 시작일"로 읽힌다. 기간의 시작이 아니라 단일 지정일이다.
3. **값이 들어올 경로가 없는 필드가 둘 있다** — `applicationEndDate`·`resultDate`는 `parseDetailPage`가 하드코딩 `null`을 반환한다(`parseDetailPage.ts:52-53`). 저장 경로는 detail 출력만 쓰므로(ADR 003 옵션 B) 어떤 row도 이 값을 가질 수 없다.

2·3이 이미 코드에 비용을 물렸다. `formatAnnouncement.ts`와 `AnnouncementCard.tsx` 두 곳에 **"이름은 시작일인데 담기는 값은 청약신청일이다"**, **"이 필드는 항상 null이라 렌더하지 않는다"**는 해명 주석이 들어가 있다. 필드를 읽는 코드가 늘어날 때마다 같은 주석을 다시 써야 한다. 곧 착수할 공고 상세 페이지가 그 다음 소비자이며, **#86의 결론이 상세 페이지가 렌더할 필드 목록을 결정**한다.

2·3은 도메인 타입 4곳(`AnnouncementListItem`·`Detail`·`Row`·`Summary`)과 DB 컬럼 3개가 함께 움직이는 스키마 변경이라 결정을 기록해둘 값이 있다.

## 고려한 선택지

### 축 1 — 필드명

#### 선택지 1-A: 리네임하지 않고 주석으로 방어

`applicationStartDate`를 유지하고, 값의 의미가 다르다는 사실을 주석·문서로 알린다.

- 장점: 변경 0. 마이그레이션 없음.
- 단점: **소비자마다 해명 주석이 복제된다.** 이미 두 곳에서 지불했고, 상세 페이지가 세 번째가 된다. 주석은 코드가 아니라서 새 소비자가 읽지 않을 수 있다.
- 단점: `applicationEndDate`가 남아 있는 한 "Start가 있으니 End도 있다"는 잘못된 기대를 필드명이 계속 유도한다.

#### 선택지 1-B: `subscriptionDate`로 리네임

소스 라벨 '청약신청일'의 '청약'을 그대로 옮긴다.

- 장점: 원본 용어·UI 문구('청약신청')와 1:1 대응.
- 단점: **이 코드베이스에서 `subscription`은 이미 웹 푸시 구독을 뜻한다** — `push_subscriptions` 테이블, `notification_preferences`, `PushSubscription` 타입, `getEnabledChannels`의 구독 조회. `announcements.subscription_date`는 "구독한 날짜"로 읽혀 도메인 어휘가 충돌한다. 하나의 단어가 두 개념을 가리키는 것은 지금의 "하나의 이름이 두 의미를 가리키는" 문제를 다른 자리로 옮기는 것에 가깝다.

#### 선택지 1-C: `applicationDate`로 리네임

`Start`만 떼어내 기간이 아닌 단일 지정일임을 드러낸다.

- 장점: '신청'이라는 뜻은 유지하면서 "기간의 시작"이라는 거짓만 걷어낸다.
- 장점: 축 2에서 `applicationEndDate`를 함께 제거하므로 **남는 `application*` 필드가 하나뿐**이라 짝을 이루는 필드가 있다는 오해가 성립하지 않는다.
- 장점: 기존 도메인 어휘(`application*`)를 유지해 다른 개념과 충돌하지 않는다.
- 단점: 이름만으로는 '청약'인지 '입주'인지 구분되지 않는다 — 소스가 노출하는 신청일이 하나뿐이므로 실질 모호성은 없지만, 사이트가 다른 종류의 신청일을 추가하면 다시 좁혀야 한다.

### 축 2 — `applicationEndDate`·`resultDate`

#### 선택지 2-A: 유지 (향후 사이트 변경 대비)

타입·컬럼을 남겨둔다. 사이트가 마감일·발표일 항목을 추가하면 파서만 고치면 된다.

- 장점: 사이트가 항목을 추가할 때 스키마 변경이 없다.
- 단점: **구조적으로 항상 null인 필드를 타입이 "있을 수 있다"고 말한다.** 모든 소비자가 `string | null`을 받아 null 분기를 쓰거나(죽은 코드), 해명 주석을 달아야(현 상태) 한다.
- 단점: 실제 유입 경로가 없는 필드는 검증할 수 없다 — 테스트도 null만 확인하므로 회귀 방어에 기여하지 않는다.
- 단점: 대비의 실효가 불확실하다. 사이트가 마감일을 추가한다면 그 형태(기간? 단일일? 회차별?)를 지금 알 수 없어, 남겨둔 컬럼이 그때 맞는 모양일 보장이 없다.

#### 선택지 2-B: 제거

타입 필드와 DB 컬럼을 걷어낸다.

- 장점: 타입이 사실과 일치한다 — "소스에 없는 것은 표현하지 않는다". 해명 주석 2건이 사라지고 새 소비자가 지불할 비용이 0이 된다.
- 장점: 되살리는 비용이 낮다 — 사이트가 항목을 추가하면 마이그레이션 1건(`ADD COLUMN`) + 파서 수정이고, 그때는 실제 응답 형태를 보고 맞는 모양으로 만들 수 있다.
- 단점: `DROP COLUMN`은 데이터 관점에서 비가역이다. 다만 현재 68건 전부 null이므로 손실할 데이터가 없다(적용 전 재확인 필요).

### 축 3 — 마이그레이션 순서

컬럼 rename은 코드와 스키마가 **동시에** 바뀌어야 한다. 어느 쪽을 먼저 해도 스큐 구간이 생긴다: 마이그레이션이 먼저면 배포 전 코드가 없어진 컬럼을 SELECT하고(`SUMMARY_COLUMNS`에 명시), 배포가 먼저면 새 코드가 아직 없는 컬럼을 SELECT한다.

#### 선택지 3-A: expand-contract (무중단)

`application_date` 추가 → 백필 → 코드 배포 → 옛 컬럼 DROP.

- 장점: 스큐 구간이 없다.
- 단점: 마이그레이션 2건 + 배포 2건의 왕복. 중간 상태에서 두 컬럼이 같은 값을 갖는 기간 동안 쓰기 경로가 둘 다 채워야 하므로 임시 코드가 필요하다.
- 단점: 무중단의 이득을 받을 트래픽이 없다.

#### 선택지 3-B: 단일 마이그레이션 + 스큐 감수

머지·배포 직후 마이그레이션 1건을 적용한다. 수 분의 스큐를 감수한다.

- 장점: 마이그레이션 1건, 임시 코드 0.
- 단점: 스큐 구간에 크롤이 1회 실패할 수 있고, 캐시 미스 시점의 목록 페이지 조회가 실패할 수 있다.

## 결정

- **축 1 — 선택지 1-C**: `applicationStartDate` → `applicationDate` (DB `application_start_date` → `application_date`).
- **축 2 — 선택지 2-B**: `applicationEndDate`·`resultDate`를 도메인 타입과 DB 컬럼에서 제거한다.
- **축 3 — 선택지 3-B**: 마이그레이션 `00004` 1건으로 RENAME + DROP을 처리하고, 배포 직후 프로덕션·테스트 양쪽에 수동 적용한다.

## 근거

- **타입은 사실을 말해야 한다.** 구조적으로 항상 null인 필드를 `string | null`로 노출하면, 그 필드를 만나는 모든 코드가 "언젠가 값이 올 수 있다"는 거짓 전제로 분기를 짜거나 주석으로 방어한다. 이미 두 곳에서 지불했고 상세 페이지가 세 번째였다 — 제거는 그 지불을 영구히 끝낸다.
- **되살리는 비용 < 남겨두는 비용.** 2-A의 대비 가치는 "사이트가 항목을 추가할 때 `ADD COLUMN`을 아낀다"인데, 그건 마이그레이션 1건이다. 반대로 남겨두는 비용은 모든 신규 소비자에게 부과되는 해명 비용이고, 게다가 그때 추가되는 항목의 모양(기간/단일일/회차별)을 지금 맞출 수 없어 남겨둔 컬럼이 재사용될 보장도 없다.
- **`subscription`은 이미 쓰인 단어다(1-B 배제).** 정확한 번역보다 코드베이스 내 유일성이 우선이다. 웹 푸시 구독과 청약을 같은 단어로 부르면 `notificationPreferences`·`push_subscriptions` 계열을 읽을 때마다 어느 구독인지 되짚어야 한다. 이름을 고치는 작업이 새 모호성을 만들면 목적을 잃는다.
- **`Start`를 떼는 것으로 충분하다(1-C).** 문제의 핵심은 "기간의 시작"이라는 거짓 함의였고, 짝인 `applicationEndDate`를 함께 없애면 그 함의를 만들 구조가 사라진다. 원본 용어를 완전히 옮기지 않는 대신 기존 어휘와의 정합을 지킨다.
- **스큐의 실제 비용이 작다(3-B).** 크롤이 스큐 구간에 실패하면 `last_board_id`가 전진하지 않아 다음 회차(1시간 뒤)에 같은 범위를 다시 훑는다 — ADR 012·007이 세운 "실패한 회차는 재관측된다" 계약이 그대로 복구 장치가 된다. 데이터 손실 경로가 없다. 목록 페이지는 캐시된 응답을 서빙한다(ADR 013). 반면 3-A는 두 컬럼을 동시에 쓰는 임시 코드를 넣고 다시 걷어내야 하는데, 그 임시 코드가 사는 기간이 스큐 구간보다 길고 리뷰·롤백 대상이 된다.
- **무손실 DROP.** 적용 시점에 `application_end_date`·`result_date`가 전 행 null임을 쿼리로 확인한 뒤 DROP한다. 파서가 하드코딩 null을 반환하므로 값이 있을 수 없지만, 스키마 파괴 작업 앞에서는 코드 추론보다 데이터 확인을 신뢰한다.

## 결과

- `src/types/announcement.ts`: 4개 타입에서 `applicationStartDate` → `applicationDate`, `applicationEndDate`·`resultDate` 제거.
- 마이그레이션 `00004_rename_announcement_date_fields.sql`:
  ```sql
  ALTER TABLE announcements RENAME COLUMN application_start_date TO application_date;
  ALTER TABLE announcements DROP COLUMN application_end_date;
  ALTER TABLE announcements DROP COLUMN result_date;
  ```
  RENAME은 인덱스·제약·트리거를 승계한다(00003 선례). 이 세 컬럼에는 인덱스가 없다.
- `parseListJson`: Step a에서 `null` 고정한 `applicationEndDate` 줄이 사라진다. `parseDetailPage`: 하드코딩 `null` 2줄과 `extractMeta`의 지역 변수명이 함께 정리된다.
- `announcementsRepository`: `SUMMARY_COLUMNS`에서 `application_end_date` 제거, row↔도메인 매핑 양방향 정정.
- `formatAnnouncement.ts`·`AnnouncementCard.tsx`: 해명 주석 삭제. 표기는 이미 '청약신청 {날짜}' 단일 날짜라 **UI 동작 변경 없음**.
- 공고 상세 페이지는 이 결정 위에서 시작한다 — 렌더할 날짜는 `postDate`(공고게시일)와 `applicationDate`(청약신청일) 둘이다.
- 마이그레이션은 프로덕션 + 테스트(`cheong-an-test`) 양쪽에 수동 적용한다(00003 선례). 적용 전 null 확인 쿼리를 실행한다.
- 이후 사이트가 마감일·발표일 항목을 노출하기 시작하면, 그 시점의 실제 응답 형태를 보고 컬럼을 추가한다. 지금의 제거는 "모르는 미래를 위해 빈 자리를 남기지 않는다"는 선택이다.
