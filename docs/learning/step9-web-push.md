# 웹 푸시 — 구독에서 발송까지, 서버가 브라우저를 깨우는 구조

웹 푸시는 "우리 서버가 사용자 브라우저에 직접 메시지를 보내는" 기술이 아니다 — **브라우저 벤더가 운영하는 푸시 서비스가 중간에서 중계**하고, 우리 서버는 그 푸시 서비스에 HTTP 요청을 보낼 뿐이다. 이 문서는 구독(9-a) → 저장(9-b) → 발송(9-c)까지 파이프라인을 완성하며 확인한 **어느 프로젝트에나 가져갈 보편 패턴**을 추린다. 청안 고유 결정(구독 의사/배달 채널 분리 스키마, 계정 단위 구독 모델)은 ADR 008 소관이다.

---

## 1. 멘탈 모델 — 등장인물 3 + 열쇠 꾸러미 1

```
[브라우저]  ──subscribe()──▶  [푸시 서비스]        [앱 서버]
 Service Worker               (FCM, Mozilla         │
     ▲                         autopush, …)         │
     │                             ▲                │
     └──── push 이벤트 ◀───────────┴── HTTP POST ───┘
           (SW가 깨어남)              endpoint로 발송
```

- **`PushSubscription`**: `subscribe()`가 만드는 구독 1건. 핵심은 세 값이다.
  - `endpoint` — 푸시 서비스가 이 구독에만 발급한 **1회용 수신 주소(URL)**. 이 URL로 POST하면 해당 브라우저의 SW가 깨어난다. 사실상 비밀값처럼 다뤄야 한다(아는 자는 누구나 발송 시도 가능 — VAPID가 이를 막는다, §2).
  - `keys.p256dh`, `keys.auth` — 페이로드 **암호화용** 클라이언트 키. 푸시 서비스조차 내용을 못 읽게 하는 종단간 암호화 재료다.
- 발송자는 이 세 값만 있으면 된다 — 그래서 서버 저장 스키마도 이 셋 + 소유자가 최소 단위가 된다.

물리 제약 두 가지가 모든 설계의 출발점이다:

1. **권한과 구독은 브라우저(프로필)마다 개별.** 계정으로 공유·이전할 수 없다 — 새 기기는 다시 권한 요청 + `subscribe()`를 해야 한다.
2. **한 브라우저 = 채널 하나.** 도착한 알림은 그 브라우저 화면에 뜬다. SW는 "지금 누가 로그인해 있나"로 수신을 거를 수 없다.

→ "구독 상태"를 계정 속성으로 만들려면 DB 모델링으로 해결해야 한다(청안의 해법은 ADR 008).

## 2. VAPID — 키 쌍이 각각 어디에 꽂히는지

VAPID(Voluntary Application Server Identification)는 "이 endpoint로 발송할 자격이 있는 서버"를 증명하는 표준이다. 키 쌍의 두 짝이 **서로 다른 시점, 다른 장소**에 꽂힌다:

| 키      | 쓰이는 곳                                           | 시점    | 노출                           |
| ------- | --------------------------------------------------- | ------- | ------------------------------ |
| 공개키  | 브라우저 `subscribe({ applicationServerKey })`      | 구독 시 | 클라이언트 OK (`NEXT_PUBLIC_`) |
| 비밀키  | 서버 발송 요청의 JWT 서명 (`web-push`가 대행)       | 발송 시 | 서버 전용                      |
| subject | 발송 JWT의 연락처 클레임 (`mailto:` 또는 https URL) | 발송 시 | —                              |

구독 시점에 공개키가 들어가므로 **채널은 그 키 쌍에 바인딩**된다. 푸시 서비스는 발송 요청의 JWT 서명을 구독 때 받은 공개키로 검증한다 — endpoint가 유출돼도 비밀키 없는 제3자는 발송할 수 없다. 따름정리: **키 쌍을 로테이션하면 기존 구독이 전부 무효**가 된다(재구독 필요). 키는 한 번 만들면 바꾸지 않는 것이 기본 운영이다.

부수 함정: `web-push generate-vapid-keys`가 주는 공개키는 base64url 문자열인데 `subscribe()`는 `Uint8Array`를 기대한다 — 변환 유틸(`urlBase64ToUint8Array`)이 한 번은 필요하다.

## 3. 구독의 죽음은 통보되지 않는다 — 만료 정리는 발송 응답으로

`PushSubscription.expirationTime`은 대부분 `null`이고, 사용자가 브라우저 설정에서 알림을 끄거나 프로필을 지워도 **서버에 아무 통보가 오지 않는다**. 죽은 채널을 알 수 있는 유일한 시점은 **발송했을 때**다:

| 응답          | 의미                                 | 처리                         |
| ------------- | ------------------------------------ | ---------------------------- |
| 201           | 푸시 서비스가 수리(배달 보장은 아님) | 성공으로 집계                |
| **410 Gone**  | 구독 만료/철회 — 표준 응답           | 해당 endpoint row 삭제       |
| **404**       | 일부 서비스(FCM)가 만료에 반환       | 410과 동일 처리              |
| 그 외 4xx/5xx | 일시 장애, 페이로드 초과(413) 등     | 삭제하지 않음(다음에 재시도) |

그래서 "저장된 만료 시각을 믿고 미리 청소"보다 **발송 시 410/404를 받으면 지운다**가 정확한 패턴이다. DB는 발송 결과로만 정리되는 **최종 일관성** 모델이 된다 — 청소 실패도 치명적이지 않다(다음 발송의 410에서 다시 잡힘).

## 4. 발송 어댑터 — 라이브러리 예외를 결과 값으로 정규화

`web-push`의 `sendNotification`은 실패를 `WebPushError`(statusCode 포함) throw로 알린다. 이걸 그대로 흘리면 두 가지가 나빠진다: ① 여러 채널에 보내는 상위 레이어가 try/catch 없이는 **한 채널 실패로 배치가 죽고**, ② 상위 레이어 타입이 라이브러리 내부 클래스에 결합된다. 어댑터에서 결과 값으로 바꾸는 게 낫다:

```ts
type SendResult =
  | { ok: true }
  | { ok: false; statusCode: number | null; message: string };
// 채널 단위 실패 → 결과 값 (Promise.all 안전)
// 전 채널 공통 오류(VAPID env 미설정) → throw (설정 오류는 표면화)
```

이 경계 덕에 합성 레이어는 `Promise.all(channels.map(send))` 후 결과만 분류하면 된다: `ok` → sent, 410/404 → expired(+삭제), 그 외 → failed(로그). **개별 실패는 격리하고, 전체가 실패할 설정 오류만 던진다**는 구분이 핵심이다.

부수 패턴: `webpush.setVapidDetails(...)`(모듈 전역 상태) 대신 `sendNotification(..., { vapidDetails })`로 **호출마다 자격 증명을 전달**하면 전역 초기화 순서 문제와 테스트 격리 문제가 사라진다.

## 5. 발송 트리거의 순서 문제 — 중복이냐 유실이냐

"이벤트 감지 → 상태 확정(DB) → 알림 발송"을 잇는 파이프라인은 발송을 어디에 두느냐로 장애 시 동작이 갈린다:

```
A. 발송 → 상태 확정     : 확정 실패 시 다음 주기에 재감지 → 같은 알림 중복 발송
B. 상태 확정 → 발송 ✅  : 발송 실패 시 그 회차 알림 유실 (다음 주기는 신규만)
```

알림은 대부분 **중복이 유실보다 나쁘다**(스팸은 구독 해지를 부른다). B를 택했다면 따름정리가 하나 붙는다 — **발송 실패가 트리거 응답을 5xx로 만들면 안 된다**. 호출자(cron)가 5xx를 보고 재시도하면 결국 A의 중복 문제로 되돌아가기 때문이다. 발송 결과는 응답 본문의 집계 필드(`push: {sent, expired, failed}` 또는 `push: {error}`)로만 표면화한다.

## 6. Service Worker 수신부 — 번들 밖의 파일이라는 제약

- SW 파일은 번들러를 거치지 않는 **정적 자산**이다(`public/sw.js`) — import 없이 self 스코프 API만 쓴다. 등록 scope는 파일 경로 기준이므로 루트 배치가 기본.
- `push` 핸들러에서 비동기 작업은 `event.waitUntil()`로 감싼다 — 안 그러면 SW가 먼저 잠들어 알림이 안 뜰 수 있다.
- 페이로드는 **서버와 SW 간의 사적 계약**이다(`{title, body, url, tag}` 등). 서버의 페이로드 빌더와 SW 파서가 같은 형태를 봐야 하고, 방어적으로 `event.data.json()` 실패 폴백을 둔다.
- `tag`가 같은 미확인 알림은 **교체**된다 — "항목별 tag"(서로 다른 알림 공존) vs "고정 tag"(최신 것만 유지)가 알림 UX의 기본 다이얼이다. 집계 알림(N건 묶음)은 고정 tag가 자연스럽다.
- `notificationclick`에서는 `matchAll`로 이미 열린 탭을 찾아 `focus()`, 없으면 `openWindow(url)` — 클릭마다 새 탭이 쌓이는 것을 막는 정석 패턴.
