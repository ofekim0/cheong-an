# 웹 푸시·인증 E2E — 무엇이 결정론적으로 자동화되고 무엇은 안 되는가

로그인·웹 푸시가 얽힌 흐름을 E2E로 자동화할 때, 순진하게 "실제 경로 그대로"를 좇으면 CI에서 계속 깨진다. 외부 비결정 의존이 여러 마디 끼어 있기 때문이다. 이 문서는 그 경계를 어떻게 긋고, 자동화 가능한 표면을 어떤 기법으로 결정론화하는지 **어느 프로젝트에나 가져갈 패턴**을 추린다. 청안 고유 결정(구독 저장 모델, 무엇을 자동화/수동으로 남겼나의 판단)은 ADR 008·010 소관이다.

---

## 1. 먼저 자동화 경계를 긋는다 — "소유 표면"만 자동화

로그인 → 구독 → 이벤트 감지 → 알림 수신 같은 흐름은 마디마다 통제 가능성이 다르다:

| 마디                    | CI 자동화 | 이유                                                      |
| ----------------------- | --------- | --------------------------------------------------------- |
| 소셜 OAuth 로그인       | ❌        | 외부 IdP, 캡차·2FA·rate limit — 결정론적으로 몰 수 없음   |
| 앱의 인증 게이팅·상태   | ✅        | 우리 코드                                                 |
| 구독 API → DB 쓰기      | ✅\*      | 우리 코드. \*단 브라우저 구독 생성은 별도 처리(§3)        |
| 브라우저 푸시 구독 생성 | ❌        | headless 브라우저엔 실제 푸시 서비스가 없어 비결정적 실패 |
| 푸시 서비스의 배달·팝업 | ❌        | 벤더(FCM 등)가 테스트 인스턴스로 배달하는 것은 관측 불가  |

핵심 판단: **"실제 경로 전체를 한 E2E로 완주"는 물리적으로 불가능**하다. 그러니 자동화할 표면(우리가 소유한 코드)과 수동 스모크로 남길 이음매(외부 비결정 의존)를 **명시적으로 갈라** 문서에 박아둔다. 안 그러면 나중에 "왜 E2E가 반쪽이지?" 하며 취약한 실측 자동화를 되살리는 회귀가 생긴다.

---

## 2. OAuth를 우회하는 세션 주입 — 쿠키는 손으로 만들지 말고 "캡처"한다

로그인 상태가 필요한 E2E에서 실제 OAuth를 돌리지 않는 표준 기법은 **세션 주입**이다:

1. admin API로 테스트 유저를 만든다(이메일 확인까지 프로그램적으로).
2. 그 유저로 로그인해 세션 토큰을 얻는다.
3. 세션을 브라우저 `storageState`(쿠키)로 주입한다.

3번의 함정: 세션이 **쿠키에 어떤 이름·인코딩으로 저장되는지**는 인증 라이브러리의 사적 계약이다(청크 분할·base64 프리픽스 등). 이걸 손으로 조립하면 라이브러리 버전이 바뀔 때 조용히 깨진다. 안전한 방법은 **라이브러리가 직렬화한 쿠키를 그대로 캡처**하는 것:

```ts
// 쿠키 저장 훅에 캡처 버퍼를 물리고 로그인시킨다 → 라이브러리가 setAll로 넘긴
// (name, value)를 그대로 storageState에 쓴다. 형식을 우리가 알 필요가 없다.
const captured: { name: string; value: string }[] = [];
const client = createServerClient(url, anonKey, {
  cookies: { getAll: () => [], setAll: (list) => captured.push(...list) },
});
await client.auth.signInWithPassword({ email, password });
// captured → { cookies: [...], origins: [] } JSON으로 저장 → 앱이 읽는 형식과 100% 일치
```

이러면 앱의 서버 클라이언트가 실제로 읽는 형식과 자동으로 맞고, 라이브러리 업그레이드에도 견딘다.

> 참고: 제품이 소셜 로그인만 지원하더라도, admin API로 password 유저를 만드는 것은 **테스트 하네스 한정**이라 제품 정책과 무관하다.

## 3. 결정론적이지 않은 브라우저 API는 프로토타입만 스텁한다

headless 브라우저에서 `pushManager.subscribe()`는 실제 푸시 서비스가 없어 비결정적으로 실패한다. 그렇다고 구독 흐름 전체를 mock하면 "우리 코드"까지 가짜가 된다. 균형점은 **비결정적인 그 한 지점의 프로토타입만 스텁**하는 것:

```ts
// PushManager.prototype만 합성 구독으로 덮는다. SW 등록·클릭·POST·서버·DB는 모두 진짜.
await context.grantPermissions(['notifications']);
await page.addInitScript(() => {
  PushManager.prototype.subscribe = async () => fakeSubscription; // toJSON 포함
  PushManager.prototype.getSubscription = async () => null;
});
```

이러면 "구독 생성"만 결정론화되고, 그 뒤의 **클릭 → 실제 fetch(POST) → 서버 인증 → DB 쓰기**는 진짜로 일어나 검증 가치가 남는다. 실제 구독 생성 경로 자체의 회귀만 수동 스모크로 넘어간다(§1의 경계).

## 4. 테스트 티어 분리 — mock 유닛이 "원리상 못 덮는 것"을 실 DB E2E가 맡는다

mock 기반 유닛 테스트는 **모듈 경계에서 값을 가로채** 배선과 분기를 빠르고 hermetic하게 검증한다. 하지만 원리상 못 덮는 게 있다:

- **실제 SQL/쿼리의 의미**: 쿼리 빌더를 mock하면 "정해준 값"이 돌아올 뿐, 실제 스키마에서 그 필터·조인이 맞는지는 검증 안 된다. 특히 FK가 없어 애플리케이션이 손으로 하는 다단계 조인은 실 DB에서만 드러난다.
- **DB가 강제하는 정책(RLS 등)**: 정책은 DB에 살아서, "남의 row가 실제로 안 보이는가"는 실 DB 세션으로만 확인된다.

그래서 두 티어로 나눈다: **mock 유닛(대다수, CI에서 시크릿 없이)** + **실 DB E2E(전용 테스트 프로젝트, 위 두 가지만 정조준)**. 새 통합 테스트를 만들기 전에 "이게 유닛이 이미 덮은 배선의 재확인인가, 아니면 실 DB로만 가능한 검증인가"를 먼저 따진다 — 전자면 중복이다.

> 함정: 실 DB E2E를 mock 유닛과 같은 `pnpm test`(hermetic 러너)에 섞지 않는다. 실 DB 의존이 유닛 러너에 secrets를 요구하게 만든다. E2E 러너(Playwright)로 분리한다.

## 5. 테스트 전용 백엔드와 env 주입

사용자 소유 데이터·인증이 얽히면 프로덕션 DB를 건드리지 않도록 **전용 테스트 프로젝트**를 둔다. 두 가지 실무 포인트:

- **프레임워크의 env 우선순위를 역이용한다**: 예컨대 Next.js는 `.env.local`을 자동으로 읽지만, **실제 `process.env`가 `.env` 파일보다 우선**한다. 그래서 E2E가 띄우는 dev 서버에 테스트 프로젝트 키를 `process.env`로 주입하면(Playwright `webServer.env`) 로컬 `.env.local`을 확실히 덮는다.
- **전용 포트**로 dev 서버를 띄운다: 개발용 서버(기본 포트)와 충돌하지 않고, "재사용된 서버가 프로덕션 env로 떠 있는" 사고를 막는다.
- **CI에선 secrets → 파일**로 만든다: 로컬은 gitignore된 `.env.test` 파일, CI는 repo secrets로 같은 파일을 생성해 로더를 한 벌로 유지한다.
